# IPL events for Home Assistant

## Purpose and authorized scope

The user requested an app that lets their Home Assistant see the authenticated IPL stream already captured from their Lutron processor. They confirmed Home Assistant Green running HA OS. The agreed architecture is IPL listener -> MQTT -> HA events and automations. Building the app does not require HA credentials. Deployment and live verification require access or a user-operated installation. The user has ended physical testing; no repeat gesture tests are required by this project.

This is an observational app. It does not change lighting, Designer programming, device enrollment, firmware, or HA automations. It cannot override the Sunnata's local touch behavior or animate its LEDs. Optional diagnostic IPL Pings are the only outbound IPL messages.

## Selected approach

Use a standalone TypeScript service with Docker packaging and a self-contained Home Assistant OS local app package. Reuse the repository's IPL parser and level conversion, and its Supervisor MQTT-service discovery helper. Keep the existing CCX/WiZ and openlutron apps separate; no new radio hardware is needed for IPL. This is processor observation rather than CCA/CCX RF sniffing. Independent RF capture would need suitable separate radio hardware/tooling, and neither processor IPL nor this supported subset promises complete device/event coverage.

Alternatives considered: a custom HA integration would eliminate MQTT but requires a new Python implementation and tighter HA lifecycle coupling; an external script posting to the HA event API would require an HA token and provide less convenient discovery. MQTT matches the existing code and publishes HA entities without needing an HA API token.

## Configuration and credentials

Configure an explicit processor host/port, IPL client certificate, private key, CA file, MQTT connection or Supervisor service discovery, namespace, instance identifier, configurable HA birth topic (default `homeassistant/status`), and an allowlist of UI object mappings. Optional `auto_discover` defaults to false; `max_discovered_objects` defaults to 128, validates integers 1–256, and limits admission of new supported observed objects. Each mapping includes a stable user-supplied identifier, display name, device ID, and UI object ID. Reject duplicate identifiers/UI objects, unsafe identifiers, wildcard/NUL-containing publish topics, invalid ports, and noninteger/out-of-range object IDs. No real household IDs, addresses, captures, or credentials are embedded in committed defaults or images.

HA OS options come from `/data/options.json`. Use slug `lutron-ipl` and a read-only `addon_config` mount explicitly mapped at `/config`. For a local installation, the current host credential directory is `/app_configs/local_lutron-ipl` (older tools expose `/addon_configs/local_lutron-ipl`); documented filenames are `ipl_client_cert.pem`, `ipl_client_key.pem`, and `processor_ca.pem`. The operator copies the existing project IPL credentials into this directory through Samba or SSH. A repository installation uses `/app_configs/<full-app-slug>`; copy the actual slug from HA rather than guessing its generated repository prefix. The compatible `addon_config` manifest mount remains read-only at `/config`. These are distinct from the normal HA LEAP pairing credentials. Certificate options resolve relative to `/config`; reject paths or symlinks escaping the credential directory. Never copy credentials into `/addons/lutron-ipl`, the staging directory, images, or examples. Validate file readability, PEM contents, certificate expiry and key/certificate consistency before connecting; explain expired credentials without attempting automatic renewal.

Declare `services: [mqtt:want]` and `hassio_api: true` with the default Supervisor role. An explicit broker wins over Supervisor discovery. Missing discovered MQTT service leaves the app offline and retrying every 30 seconds, with a 5-second timeout per discovery request; it does not silently start without a publication destination. Standalone Docker uses the same configuration contract with an explicit options file, explicit broker, and read-only certificate volume. MQTT passwords use HA's password schema and never appear in logs. Missing credentials or invalid configuration fail clearly before opening either connection. Packaging must not depend on files outside the app's Docker build context.

Use the proven OpenSSL transport with `-CAfile` and `-verify_return_error` enabled. The default compatibility policy verifies the server certificate chain against the explicitly supplied CA, but does **not** verify that the configured IP/hostname identifies a particular processor: the successful capture did not use `-verify_hostname` or `-verify_ip`. State this boundary in configuration help and installation documentation, rather than calling it processor identity validation. Support an optional expected certificate DNS name or IP with the corresponding OpenSSL verification option; a mismatch fails closed. Do not invent an expected identity from the configured LAN address. Credentials must remain outside generated packages and fixtures.

## IPL input contract

Parse binary frames directly, including supported version-dependent headers, ACK/Response framing, fragmented packets, and multiple frames per chunk. Reuse the body decoder and frame layouts, but wrap the existing permissive parser with strict validation: accept versions 1-3 and known message types 0-5, preserve supported unknown operation bodies for debugging, and require frame magic at the next boundary. Retain incomplete magic/header/body bytes, including Resend headers; distinguish incomplete input from invalid headers. Bound the unconsumed buffer at 128 KiB and impose a 10-second incomplete-frame deadline independent of unrelated completed frames. Malformed input terminates the session rather than silently scanning for another magic marker. Never parse pretty-printed CLI output.

For each configured UI, emit a `level_adjustment` event only on Telemetry operation 1, object type 9, matching UI object ID, property Level (1), and a valid two-byte level value. Use the existing level16 conversion and reject values beyond its valid level range. Include device ID, UI object ID, percentage, wire value, receipt timestamp, per-connection `session_id`, and `source_kind: ui_level_report`. Preserve separate reports of repeated percentages; no claim is made that every same-level physical touch emits telemetry. This event name describes observed UI telemetry, not a validated touch start/release detector. Label the HA entity and installation documentation experimental.

The app does not request UI state. An unsolicited initial/cached UI report after reconnect cannot currently be distinguished from a fresh adjustment. Do not promise to exclude processor-side snapshots or call a receipt timestamp a physical-gesture timestamp. The no-replay contract below applies to app/MQTT buffering only. Example automations are opt-in and explain this limitation; they are not installed or enabled by the app. If a later implementation adds bounded startup suppression, document its potential to drop the first adjustment and do not claim it validates freshness.

Historical offline evidence contains UI-Level reports during two touch rounds, with none in the app, local-button, or keypad-scene control windows. Continuous updates, exact release semantics, general device compatibility, and same-level touch emission remain unverified. The app does not turn generic zone levels into physical-touch events.

Provide optional unretained decoded-frame JSON on a separate debug MQTT topic so the IPL stream can be inspected, not only the selected UI signal. It is disabled by default, documents that it exposes all observed IPL objects rather than only the UI allowlist, and includes raw body hex plus decoded headers, receipt timestamp and session ID rather than attempting source attribution. Bound debug publication rate/backpressure; report drop counts as diagnostics without retaining or caching frame payloads.

## Supported automatic observations (v0.2.0)

The authoritative exact decoder and identity requirements are in [event-expansion-plan.md](event-expansion-plan.md). Observe only supported exact payload shapes: type-57 button press/release; type-38/66 event occupancy; runtime occupancy for type 38/2/66 property 16; type-9/15/3/198 Level property 1 (UI/zone/load/shade); type-3 current Level property 4; type-2/133 scene selection property 67; type-2 area-lighting property 91; and type-15 GoToLevel command operation 13. Unsupported operation 38, RPC, configuration, object/property combinations, and widths create no semantic entity/event. This release does not add an outbound command writer.

Automatic observations carry numeric `system_id`, `object_type`, `object_id`, `operation_id`, optional `property_number`, `event_type`, `source_kind`, receipt timestamp, and session ID. Levels retain their u16 wire value through `0xfeff` and convert to rounded percentage. Occupancy retains unknown numeric statuses; known 1/3/4/255 map to unknown/occupied/unoccupied/disabled. Scene selection/lighting states stay numeric; opaque button-release/type-66 event bytes stay `trailing_hex`. GoToLevel includes level, `originator_feature`, `fade_quarters`, and `delay_quarters`; it cannot establish original client, RF delivery, device execution, or outcome. The [public signal reference](../app/DOCS.md#passive-discovery-and-supported-observations) lists event names and fields.

Automatic discovery admits only a supported observation, so silent objects cannot be discovered passively. Generic names describe IPL objects with numeric system/type/object identity and do not infer device IDs, rooms, components, or radio family. Fixed event types per object type describe its supported families. IDs derive from validated numeric descriptors as `auto_s<S>_t<T>_o<O>`. Existing manual UI mappings retain their identities, `level_adjustment` event and `source_kind: ui_level_report`; they suppress matching automatic UI entities, including restored descriptors.

Every family can repeat reports or deliver processor startup/cached reports. Receipt time is not physical action time. There is no freshness claim or attempt to replay the initial report if HA has not yet subscribed after discovery.

## MQTT and HA entities

Publish retained HA discovery for one MQTT event entity per configured UI, with event type `level_adjustment`. Generate discovery from the configured mappings rather than waiting for the first UI report. Publish a connection-health binary sensor and retained availability; initialize IPL health offline, and require both MQTT and a healthy IPL session for event-entity availability. Keep the connection-health sensor available while MQTT works so it can show IPL disconnected. Use an MQTT last will to mark the app offline on process loss.

Event messages and debug messages are never retained. Use clean MQTT sessions, QoS 0, explicit `queueQoSZero: false`, a connected gate, and bounded publisher backpressure. Drop observations while MQTT is unavailable or a bounded write is congested; do not keep an application event cache. This is best-effort delivery, not an exactly-once guarantee. A process/session disconnect resets pending parser bytes and liveness. Subscribe to the configured HA birth topic on every broker connection. HA birth and MQTT reconnect republish discovery and current health, never old events. Include stable entity identities so renaming does not create duplicates. Independent installs require independent namespaces/instance identifiers. Persist only the app-owned discovery-topic inventory and validated numeric descriptors under `/data`, never event payloads/timestamps/last values; clear removed mappings with retained empty discovery payloads, without touching another integration's entities. Automatic configs use a separate discovery node `event/<uniquePrefix>auto/<descriptor.id>/config`, unique ID `<uniquePrefix>auto:<descriptor.id>`, and event topic `<root>/auto/<descriptor.id>/event`, preventing collisions with legal manual IDs. Bound descriptor file size/count, reject symlinks/corrupt inventories and duplicate identities, and atomically write mode 0600. Quiet descriptors restore discovery at restart, HA birth, and broker reconnect. Disabling automatic discovery clears only its owned configs. Admission stops at the configured cap while existing objects continue; lowering the cap preserves existing objects up to the global 256 bound. Bound automatic reports to 50 per second plus socket/inflight limits, and expose dropped-observation counters.

## Lifecycle

Connect/reconnect with bounded backoff (1 second initially, doubling to a 30-second maximum) and no overlapping IPL child processes. Consider IPL healthy after receiving a valid frame; require one within 30 seconds of starting the connection and terminate the session after 75 seconds without valid inbound frames. Diagnostic Pings every 20 seconds keep the stream active, as in the existing capture helper, without making lighting commands. Reset backoff only after a session has stayed healthy for 60 seconds. Signal handlers stop timers, terminate and reap OpenSSL with a bounded escalation to force termination, publish offline if MQTT is connected, and close MQTT. Logs contain connection state and error categories without certificate contents, passwords, arbitrary OpenSSL output, or full raw frames.

## Packaging

Deliver the service and its tests in the separate lutron-ipl-app repository, a documented reproducible staging command that produces a self-contained HA app directory, an example configuration with placeholders, installation instructions for Home Assistant Green with HA OS, and an example HA automation that uses the event's level. Package only required source/build output, locked runtime dependencies, and documentation. Home Assistant Green / aarch64 is the primary deployment target; support amd64 as well without privileged access or radio devices. Standalone Docker is a secondary launch option for the same service, not a separate deployment target requiring HA migration.

Stage a complete app folder for transfer to `/addons/lutron-ipl`, using an allowlist of files rather than copying the entire checkout. The operator uses Samba's addons share or the HA SSH app, refreshes the local app store, installs `Lutron IPL Events`, copies credentials into the separate app-config directory, configures the explicit processor/mappings, and starts the app. Current UI labels may say Apps or Add-ons depending on the installed HA release. Include a manifest, Dockerfile with explicit pinned multi-architecture base and required HA labels, startup entrypoint, minimal locked runtime dependency manifest, README/DOCS, and configuration example. Compile JS during packaging/build or lock the runtime transpiler; no floating `npx` downloads at startup. Install OpenSSL explicitly. Use ordinary container networking, read-only app-config access, and no USB mapping, host networking, Docker API, or privileged capabilities. Local installation does not require publishing a Git repository or container image.

## Verification and completion

Verify event filtering and level conversion against sanitized fixtures derived from the saved capture, including negative controls. For v0.2.0 verify exact supported payload shapes and unknown/malformed rejection, system/type/object identity separation, generic fixed event types, descriptor validation/security/limits, persistence without payloads, disabled-auto owned cleanup, manual UI suppression, cap changes, initial-config/report timing, and automatic rate/backpressure drops. Exercise partial magic/header/body and Resend frames, unsupported versions/types, junk prefix, invalid payloads/lengths, repeated levels, buffer bounds, incomplete-frame timeout, session reset, initial UI report semantics, capture loss, MQTT disconnection/reconnection races, HA birth, missing-broker discovery timeout/retry, removed mapping discovery cleanup, slow-publisher drops, and graceful shutdown/child reaping. Simulated TLS fixtures verify valid chains, wrong CA, expired/mismatched credentials, and optional expected-identity failure without connecting to household devices. Run focused existing IPL/Supervisor tests and TypeScript checks. Validate that a staged app has a complete build context and excludes real config/certificates/captures. Build/run Docker if a usable Docker engine is present; explicitly report if this cannot be verified locally.

Local implementation completion means the packaged app and offline checks are ready. Installation into HA, successful live MQTT delivery, and behavior of user-created automations are separate verification steps and must not be claimed without evidence. No extra physical gesture trials are prerequisites.
